# 安全策略与威胁模型

本仓库是**公开**的，后端也一并开源。这份文档说明：为什么这没问题、我们靠什么保证安全、以及哪些东西绝不能进仓库。

---

## 一句话立场

> **开源不减安全性。** 减安全性的是两件事：**把秘密写进代码**，以及**不修已知问题**。
> 本项目遵循 Kerckhoffs 原则：安全性只依赖密钥的保密，不依赖实现与路径的保密。

而且对本项目而言，"靠保密换安全"从来不是可选项：站点本身是公开的（GitHub Pages + 两处镜像），API 形状迟早公开，`/author` 这类路径也会出现在源码里。**我们能依赖的只有：高熵凭证、限流锁定、最小权限、审计与备份。**

### 一个实证

后端原型跑起来的第一个小时就抓到两个真 bug：

| bug | 与"代码是否公开"的关系 |
| --- | --- |
| 畸形百分号编码让整进程崩溃（`decodeURIComponent` 抛错且不在 `try` 内） | **无关**。闭源服务一样会崩；开源反而可能被人提前报告 |
| 作者键与条目 slug 重名导致节点被覆盖 | **无关**。这是数据建模问题 |

反过来，公开源码让"这行代码安全吗"可以被任何人复核——对一个只有 1–2 名维护者的志愿项目，这是**净收益**。

## 攻击面与对策

| 攻击面 | 风险 | 对策 |
| --- | --- | --- |
| **凭证验证**（`POST /v1/auth/session`） | 在线爆破、账号枚举 | 32 字符 ≈190 bit 令牌；按 `pin + IP` 限流与连续失败锁定；错误 pin 与错误 token 返回**同一条**信息 |
| **令牌存储** | 库被读走 → 凭证泄露 | 只存 `sha256(token + pepper)`；明文只在签发时出现一次；胡椒走环境变量（缺失或过弱拒绝启动） |
| **会话** | cookie 被窃、跨站请求 | `HttpOnly + SameSite=Lax`；生产强制 `Secure`；吊销令牌连带吊销会话 |
| **投稿上传（zip）** | **本项目最大的攻击面** | 隔离解压（`inbox/`，绝不在最终路径解压）、路径穿越与符号链接拒绝、zip bomb 压缩比上限、文件数与总量上限、类型白名单、未审素材与公开路径物理隔离 |
| **未审内容外泄** | 草稿被公开 | 公开接口只读 `published_revision_id` 非空的节点；`accounts`/`tokens`/`sessions`/`recovery_codes` 独立成表，导出路径**只连接 `nodes` 与 `edges`** |
| **越权改他人条目** | 作者互改 | 权限只看 `maintains` 边，不看身份类型；staff 例外 |
| **依赖漏洞** | 已知 CVE 被自动化扫描利用 | 后端目前**零运行时依赖**（`node:http` + 内置 `node:sqlite`），依赖面越小越好；引入依赖时接 Dependabot |
| **部署配置泄露** | 定向攻击 | 生产配置（域名、反代、面板路径）不进公开仓库；只保留 `.env.example` |
| **数据与素材** | 库文件、上传原件 | `data/` 已 gitignore；每日异地备份（见设计文档 §11.4） |

## 秘密清单：什么绝不能进仓库

| 东西 | 存放位置 |
| --- | --- |
| `TAVERN_TOKEN_PEPPER` | 服务器 `.env`（已 gitignore）；生产要求 ≥ 32 字符随机串 |
| 作者令牌明文 | **只在不落库的签发输出里出现一次**，之后不可找回 |
| 数据库文件 | `tavern-server/data/`（已 gitignore） |
| SFTP 凭证、镜像站 bearer token | GitHub Secrets（既有 workflows 已是如此） |
| 生产域名与反代配置 | 部署侧，不进公开仓库 |

**已内置的护栏**

- `.gitignore` 覆盖 `.env` / `.env.*` / `*.pem` / `*.key`
- `npm run check:secrets`：扫描所有被跟踪的文本文件，命中私钥、常见平台令牌、硬编码凭证即失败
- 配置 fail-closed：生产环境（或绑定非回环地址）使用默认胡椒或短胡椒时**拒绝启动**
- 单测覆盖：`tests/scan-secrets.test.mjs`、`tests/router.test.mjs`

> ⚠️ **git 历史是永久的。** 一旦某次提交带上了凭证，删掉≠没泄露，必须**立即作废重发**。
> 历史扫描请用 `gitleaks detect --no-banner`（本仓库的扫描只看当前工作树）。

## 报告漏洞

发现安全问题请**不要开公开 issue**，改为：

1. 邮件或私信联系维护者（联系方式见站点首页「联系我们」）；
2. 或使用 GitHub 的 [Private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability)（仓库 Security 标签页 → Report a vulnerability）。

请附上：影响范围、复现步骤、以及你希望我们如何处理。我们会在确认后（若你同意）在修复说明里致谢。

**我们不承诺的**：不设漏洞赏金，不承诺响应时限——这是志愿者项目。但**只要确认是真问题，我们一定会修**。

## 明确接受的风险（不打算修）

| 项 | 为什么接受 |
| --- | --- |
| `/author` 等管理路径出现在公开源码里 | 隐蔽性本来就不是安全措施；真正的防线是高熵凭证 + 限流 + 审计。搜索引擎收录由 `noindex` 与 `X-Robots-Tag` 单独处理 |
| 作者可以给自己项目打已有标签（直通生效） | 低风险且有事后摘除能力；真正的关口放在"创建新标签"上（设计文档 §5.1.2） |
| 审核由人工完成，存在主观性 | 这是策展型站点的性质决定的，不是技术问题 |
